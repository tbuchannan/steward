# Styling

## Decision

Steward will use Tailwind CSS as its styling framework and shadcn/ui as its component system.

Tailwind CSS will provide utility-based styling, responsive design, themes, and design tokens.

shadcn/ui will provide customizable React component implementations that are added directly to Steward's source code.

## Selected Technologies

The confirmed styling technologies are:

- Tailwind CSS
- shadcn/ui
- CSS custom properties
- React
- TypeScript

Supporting packages used by individual shadcn/ui components may include:

- Radix UI primitives
- Base UI primitives
- Class-name utilities
- Animation utilities
- An icon library

The exact supporting dependencies will be determined by the shadcn/ui configuration and the components added to the project.

## Responsibilities

### Tailwind CSS

Tailwind CSS is responsible for:

- Layout
- Spacing
- Typography
- Colors
- Borders
- Shadows
- Responsive design
- Theme variants
- State variants
- Utility-based styling

### shadcn/ui

shadcn/ui is responsible for providing the starting implementations for reusable interface components such as:

- Buttons
- Inputs
- Selects
- Dialogs
- Dropdown menus
- Popovers
- Tooltips
- Tabs
- Tables
- Sheets
- Drawers
- Alerts
- Toasts
- Form controls

### Steward

Steward owns:

- Branding
- Design tokens
- Theme customization
- Component composition
- Dashboard widgets
- Financial data displays
- Application-specific interface behavior
- Accessibility of completed workflows

## Why Tailwind CSS

Tailwind CSS was selected because it provides:

- A consistent utility-based styling model
- Strong support for responsive layouts
- Colocated styling within React components
- Theme customization
- Design-token support
- Strong editor tooling
- Integration with Vite
- Integration with shadcn/ui

Tailwind reduces the need for large component-specific stylesheets while still allowing reusable abstractions where they provide clear value.

## Why shadcn/ui

shadcn/ui was selected because:

- Component source code is added directly to the repository.
- Components can be modified to fit Steward.
- Components are designed to work with Tailwind CSS.
- Components provide accessible interaction foundations.
- Steward is not restricted to a fixed visual theme.
- Individual components can be added only when needed.

shadcn/ui should be treated as a component-code distribution system rather than a closed component package.

The generated components belong to Steward's source code, but they may still depend on supporting runtime packages.

## Tailwind Integration

The React and Vite application should use the current Tailwind CSS Vite integration.

Conceptually, the Vite configuration will include the Tailwind plugin:

```ts
import tailwindcss from "@tailwindcss/vite";
```

The application's main stylesheet will import Tailwind:

```css
@import "tailwindcss";
```

The exact setup should follow the installed Tailwind CSS version.

Legacy configuration patterns should not be added unless required by a specific plugin or project constraint.

## shadcn/ui Integration

shadcn/ui should be initialized for the React and Vite application.

The setup will define choices such as:

- Component style
- Base color
- CSS variable usage
- Icon library
- Import aliases
- Component output directory
- Monorepo or single-application structure

The project should maintain a `components.json` file generated by the shadcn CLI.

A likely component location is:

```text
src/components/ui/
```

If Steward uses a monorepo with a shared UI package, the location may instead be:

```text
packages/ui/src/components/
```

The final path depends on the repository architecture decision.

## Component Ownership

Components added through shadcn/ui become part of Steward's codebase.

This means Steward may:

- Modify their markup
- Change their styles
- Add application-specific variants
- Remove unused behavior
- Fix accessibility issues
- Update dependencies independently

Changes to generated components should be reviewed like any other application code.

The project should avoid repeatedly overwriting customized components without reviewing CLI-generated changes.

## UI Architecture

The interface should be built in layers:

```text
Tailwind CSS and design tokens
                ↓
Primitive UI components
                ↓
Shared application components
                ↓
Feature components
                ↓
Pages and route layouts
```

### Primitive UI components

Primitive components are generic controls and containers.

Examples include:

- Button
- Card
- Input
- Label
- Select
- Checkbox
- Dialog
- Sheet
- Table
- Tabs
- Badge
- Tooltip

These should generally live in:

```text
components/ui/
```

### Shared application components

Shared components combine primitives into patterns used across multiple features.

Examples include:

- PageHeader
- EmptyState
- ErrorState
- ConfirmationDialog
- SearchField
- DataTableToolbar
- PaginationControls
- ThemeToggle
- CurrencyDisplay

### Feature components

Feature components represent Steward concepts.

Examples include:

- AccountCard
- TransactionRow
- TransactionTable
- BudgetProgress
- BudgetCategoryRow
- NetWorthSummary
- SpendingSummary
- RecentTransactions
- DashboardWidget

Feature components should live close to the feature that owns them.

## Design Tokens

The visual system should use shared design tokens rather than unrelated hard-coded values.

Tokens should cover:

- Background colors
- Surface colors
- Text colors
- Muted text
- Borders
- Primary actions
- Destructive actions
- Success states
- Warning states
- Focus rings
- Border radius
- Shadows
- Spacing where appropriate

CSS custom properties should be used for theme-aware values.

Conceptually:

```css
:root {
  --background: ...;
  --foreground: ...;
  --card: ...;
  --card-foreground: ...;
  --primary: ...;
  --primary-foreground: ...;
  --destructive: ...;
  --border: ...;
  --ring: ...;
}
```

The exact token names should remain compatible with the selected shadcn/ui setup where practical.

## Brand Color

The current design direction uses purple as Steward's primary accent.

The exact shade has not yet been finalized.

The selected purple should:

- Meet contrast requirements
- Work in light and dark themes
- Remain legible for text and controls
- Avoid conflicting with semantic financial colors

The application should not use purple for every visual emphasis.

## Financial Colors

Financial information may use semantic visual treatment for:

- Income
- Expenses
- Positive balance changes
- Negative balance changes
- Remaining budget
- Overspending
- Warnings

Color must not be the only way meaning is communicated.

For example, income and expenses should also use:

- Labels
- Signs
- Icons where appropriate
- Accessible text
- Clear table headings

A negative financial value is not always an error, so destructive UI colors should not automatically be used for every expense.

## Typography

Typography should prioritize readability and information hierarchy.

The application should define consistent styles for:

- Page titles
- Section headings
- Card titles
- Body text
- Labels
- Supporting text
- Captions
- Financial values
- Table content

Decorative fonts should be avoided for primary application content.

Tabular numerals should be considered for columns containing monetary values so that digits align consistently.

## Layout

### Desktop

The desktop application may use:

- Persistent sidebar navigation
- Application header
- Main content area
- Multi-column dashboard grid
- Data tables
- Side panels where appropriate

### Tablet

Tablet layouts may use:

- Collapsible navigation
- Reduced dashboard columns
- Scrollable tables or card alternatives
- Touch-friendly controls

### Mobile

Mobile layouts should use:

- Drawer or sheet navigation
- Single-column content
- Larger touch targets
- Condensed summaries
- Mobile-appropriate transaction layouts
- Dialog alternatives where full-screen interaction is clearer

Responsive behavior should be designed per workflow rather than implemented as a simple visual shrink of the desktop interface.

## Responsive Design

All major workflows should support:

- Mobile
- Tablet
- Desktop
- Large desktop

Tailwind responsive variants should be used for layout changes.

The application should avoid maintaining completely separate mobile and desktop component trees unless the interaction model genuinely requires it.

## Dark Mode

Steward should support:

- Light mode
- Dark mode
- System preference

The user's explicit theme choice should persist between sessions.

Theme behavior should be applied through shared tokens rather than separate component implementations.

Every component added to the application should be checked in both light and dark themes.

## Styling Guidelines

Prefer:

- Tailwind utility classes
- Shared design tokens
- Reusable variants
- Component composition
- Semantic HTML
- Responsive variants
- Clear class organization

Avoid:

- Inline `style` properties for ordinary styling
- Large global stylesheets
- Deep selector nesting
- Unexplained arbitrary values
- Duplicated class combinations
- Unnecessary wrapper elements
- Styling based on fragile DOM structure

Inline styles remain acceptable for genuinely dynamic values that cannot reasonably be represented through Tailwind classes or CSS variables.

## Class Composition

Conditional classes should use the utility selected by the shadcn/ui setup.

A common pattern is a shared `cn` helper that combines class values and resolves conflicting Tailwind classes.

Conceptually:

```ts
cn("base-classes", isActive && "active-classes", className);
```

Reusable component variants should use a consistent variant-management approach.

The exact variant utility should follow the generated shadcn/ui component setup.

## Global CSS

Global CSS should remain limited to concerns that are genuinely global.

Examples include:

- Tailwind import
- Theme tokens
- Base element styles
- Font declarations
- Document background
- Selection styling
- Application-wide accessibility utilities

Feature-specific styling should remain close to the relevant component.

A likely file is:

```text
src/styles/globals.css
```

The final path may differ based on repository structure.

## Icons

Steward should use one primary icon library consistently.

The exact library will be selected during shadcn/ui initialization.

Icons should:

- Reinforce labels rather than replace unclear text
- Have accessible names when they communicate meaning
- Be hidden from assistive technology when purely decorative
- Use consistent sizing
- Avoid unnecessary decoration

The project should not mix multiple icon libraries without a clear reason.

## Data Tables

Transaction and account tables should use shared table primitives and feature-specific composition.

Tables should support:

- Clear headings
- Keyboard-accessible controls
- Sort-state indication
- Loading states
- Empty states
- Error states
- Responsive behavior
- Consistent monetary alignment

On smaller screens, a card or list representation may be more usable than forcing a wide table.

## Forms

Form interfaces should compose shadcn/ui controls with the selected form library and Zod schemas.

Form components should support:

- Labels
- Descriptions
- Required-state communication
- Field validation
- Server errors
- Disabled states
- Submission progress
- Keyboard interaction
- Accessible error association

Placeholder text should not replace visible labels.

## Feedback Components

The application should use the appropriate feedback pattern for each situation.

Examples include:

- Inline field errors for validation
- Alerts for page-level problems
- Toasts for brief non-blocking confirmation
- Dialogs for destructive confirmation
- Skeletons for initial loading
- Progress indicators for longer operations
- Empty states when no records exist

Toasts should not be the only location for important errors or information that users may need to reference.

## Animation

Animation should support comprehension rather than decoration.

Appropriate uses include:

- Dialog transitions
- Sheet transitions
- Expand and collapse behavior
- Loading indicators
- Subtle state changes
- Toast appearance and dismissal

Animations should:

- Remain brief
- Avoid delaying actions
- Respect reduced-motion preferences
- Avoid moving financial data unnecessarily

## Accessibility

shadcn/ui provides accessible foundations, but Steward remains responsible for the accessibility of completed interfaces.

All workflows should support:

- Keyboard navigation
- Visible focus indicators
- Semantic HTML
- Screen readers
- Sufficient contrast
- Accessible labels
- Accessible validation messages
- Reduced-motion preferences
- Logical focus management

Accessibility should be verified after components are composed, not assumed from the primitive component alone.

## Performance

Tailwind CSS performs styling generation during the build process rather than through a client-side styling runtime.

Steward should:

- Avoid generating class names dynamically from unbounded strings
- Prefer complete class names that Tailwind can detect
- Avoid importing unused component implementations
- Add only the shadcn/ui components needed
- Keep animation and visual effects restrained
- Monitor the frontend bundle as the application grows

## Testing

Styling and component tests should cover behavior rather than exact implementation details.

Tests should verify:

- Keyboard interaction
- Dialog focus behavior
- Theme switching
- Responsive navigation
- Form states
- Disabled states
- Loading states
- Empty states
- Error states
- Accessible labels and roles

Visual regression testing may be introduced later if it provides enough value.

## Documentation

Application-specific UI patterns should be documented when they become reusable.

Useful documentation may include:

- Color and token usage
- Typography hierarchy
- Form patterns
- Table patterns
- Empty states
- Confirmation behavior
- Mobile navigation
- Dashboard widget conventions

The project should not attempt to document every Tailwind utility.

## Non-Goals

The initial styling architecture will not use:

- CSS Modules
- Styled Components
- Emotion
- Material UI
- Chakra UI
- Ant Design
- Bootstrap
- Multiple competing component systems

These technologies should not be introduced without revisiting the styling decision.

## Success Criteria

The styling architecture is successful when:

- Tailwind CSS provides a consistent styling model.
- shadcn/ui provides reusable and customizable component foundations.
- Component source remains owned by Steward.
- Supporting dependencies are kept understandable.
- Light, dark, and system themes work consistently.
- Responsive workflows remain usable across device sizes.
- Business components compose shared primitives.
- Accessibility is preserved after component composition.
- New pages can be built without inventing unrelated visual patterns.
